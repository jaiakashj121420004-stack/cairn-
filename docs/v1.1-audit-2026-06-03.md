## 2. P&L → `decimal.js` conversion

**File:** `apps/desktop/electron/services/pnl-calculator.ts`
**Why:** §19.5 bans floats in `pnl-calculator.ts`. The prior code was integer-*encoded*
(cents/tenths/hundredths) — correct in spirit — but its three divisions (`/1000`,
`/slPips`, `/accountSizeCents`) and the duration `/60_000` ran through IEEE-754 before
`Math.round`. A money-adjacent app must round the **exact rational**, not a float
approximation of it (§2.5).

**What changed:**
- Every money/pip value flows through `Decimal`; `+ - * /` replaced by `Decimal` methods.
- A single explicit round at each boundary via `roundToInt`, using **`ROUND_HALF_CEIL`**
  — the decimal.js mode that matches the prior `Math.round` (ties toward +∞) **exactly**.
  This makes the change precision-only: no value that previously rounded one way now
  rounds the other. (Note: `ROUND_HALF_UP` was tried first and rejected — it rounds ties
  *away from zero*, which would silently shift losses on `.5` boundaries.)
- Integer input/output contract is unchanged; all consumers in `electron/ipc/trades.ts`
  are unaffected.

**Tests added:** `apps/desktop/tests/unit/pnl-calculator.test.ts` (11 tests, `fast-check`):
- **Golden pins** — EURUSD long +50p/0.50 lots → +$250.00 / +2.50R / 250 bps;
  loss symmetry; divide-by-zero guards (slPips=0, account=0).
- **Associativity within decimal precision** — `(a·b)·c === a·(b·c) === (a·c)·b` and
  division order-independence, exactly (the float trap the conversion closes).
- **Scale-invariance of the R-multiple** — scaling entry/exit/slPips by integer `k`
  leaves `pnlR` **exactly** unchanged, while `pnlCents` scales by `k` (sanity check that
  the invariance is non-trivial).
- **Invariants** — outputs always integer; direction-flip negates P&L up to a documented
  1-unit tie-rounding skew (a true property of the half-toward-+∞ encoding, present under
  the old `Math.round` too — *not* introduced by this change).

## 3. Findings

### F-1 — Orphan `accounts.max_daily_loss_pct` REAL column (low severity)

`electron/db/schema.ts:79` declares `maxDailyLossPct: real('max_daily_loss_pct')`. This is
the only `real`/`float`/`double` column in the schema; every other percent is integer
basis points (`risk_pct_bps`, `default_risk_pct`, `close_percent_bps`).

- **Runtime impact: none.** No code reads `accounts.maxDailyLossPct`. The live circuit
  breaker reads an **integer** `maxBps` from the `account_rules` config and computes the
  threshold with integer math (`rules/max-daily-loss-pct.ts`).
- **Why it still matters:** it is a money-adjacent `real` column, contrary to Locked #36
  ("no monetary or pip column stored as `real`/`float`") and §19.5. It is the kind of
  latent float that the partials reconciliation (migration 0004) already removed.
- **Recommendation:** drop the column in a future **append-only** migration (with a
  forward test), once confirmed unreferenced by any persisted data. Deferred here — out of
  this task's scope (pnl-calculator + tests + report), and a column drop warrants its own
  migration + review.
- **Guardrail added now:** the new migration test asserts the float-column set equals
  *exactly* `['accounts.max_daily_loss_pct']`, so this finding is visibly tracked and any
  **new** float column fails CI immediately.

## 4. Migration test: forward + re-run idempotency (fresh & seeded)

**File:** `apps/desktop/tests/integration/migrations.test.ts` (+3 tests, 13 → 16).

- **On "backward":** the Drizzle SQLite chain is **forward-only** — there are no
  down/rollback files. The meaningful backward-safety guarantee for such a chain is
  §19.6's "re-running on the post-state is a no-op," which production gets from Drizzle's
  `__drizzle_migrations` bookkeeping.
- **Why not the real migrator:** `better-sqlite3` is ABI-built for Electron's Node
  (`NODE_MODULE_VERSION 137`) and will not load under the vitest runtime (130) — which is
  why the whole suite uses `sql.js`. The test emulates Drizzle's applied-migration gate
  with an `__applied` tracking table.
- **Coverage:**
  - *Fresh DB* — applies the whole journaled chain forward; a second pass applies **0**
    statements and the schema snapshot is byte-identical.
  - *Seeded DB* — forward, then `runSeed()` in production order (after migrate); asserts
    seed counts (19 pairs / 10 setups / 5 killzones / 1 firm / 8 settings); re-running the
    migrator leaves schema **and** data untouched.
  - *Float-column ratchet* — see F-1.
- Existing data-bearing forward tests (0004 partials conversion, 0009 phase-2 backfill)
  already cover "data present *before* a migration survives it"; those remain green.
