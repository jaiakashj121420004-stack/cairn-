# Cairn — Live Broker Integration (Wave 4)

**Status:** specification (binding plan). Not yet built.
**Scope:** v1.2 Wave 4 — the only paid/optional wave. See `docs/roadmap-v1.2.md` §4 (Wave 4) and `prompts.md` §8.7 for the build prompts.
**Source of truth:** this file is authoritative for the live-broker design. `docs/integrations-future.md` §11.1 keeps a short pointer here.

> A cairn marks the trail. This wave lets the trail mark itself — the broker tells Cairn what you actually did, the moment you did it — without ever letting Cairn touch the trade.

---

## 1. What this wave delivers

When the trader takes a trade in **MetaTrader 5** or **cTrader**, that fill is captured by Cairn automatically — entry, direction, lots, prices, times, partials and the close — with no re-typing. Two platforms, one internal pipeline.

It also delivers the genuine realisation of **prevention over detection** (`CLAUDE.md` §2.1): because Cairn now watches the *live* position, it can warn the instant a planned-vs-actual divergence breaches a rule — a stop widened against the trade, a position sized up mid-trade, an over-trade past the daily limit — something a statement import (Wave 3) can only catch hours later.

What it explicitly does **not** do: place, modify, or close orders. Cairn reads; it never writes to the broker. This is a locked decision (`CLAUDE.md` §14 #6 and the Wave 4 additions) and a hard safety boundary (financial-action policy). The bridge has no order-execution code path at all.

---

## 2. The two transports

cTrader has a real API; MT5 does not. So the two platforms reach Cairn by different roads, but both normalise to the same internal `BrokerEvent` stream (§4).

### 2.1 MT5 — local Expert Advisor → localhost socket bridge (decided)

MT5 has no outbound API for third-party apps. The chosen path keeps everything **local-first** (`CLAUDE.md` §2.4): a small Expert Advisor (EA) runs *inside* the user's MT5 terminal and pushes events to a Cairn listener on `127.0.0.1`. Nothing leaves the machine.

```
┌────────────────────────┐        localhost TCP/WebSocket        ┌──────────────────────────┐
│  MetaTrader 5 terminal  │  ──────  JSON BrokerEvent  ───────▶  │  Cairn desktop (main proc) │
│   └─ Cairn Bridge EA     │        (127.0.0.1:<port>)            │   └─ MT5 ingest listener    │
│      OnTradeTransaction  │  ◀─────  heartbeat / ack  ─────────  │                            │
└────────────────────────┘                                       └──────────────────────────┘
```

- **EA responsibility (MQL5):** subscribe to `OnTradeTransaction` (the event MT5 fires on every deal/order/position change), serialise each transaction to the `BrokerEvent` JSON shape, and send it over the socket. The EA is read-only — it never calls `OrderSend`/`OrderModify`/`OrderClose`. It also emits a periodic heartbeat so Cairn can show connection status.
- **Transport:** localhost socket. MQL5's native `Socket*` functions speak raw TCP; the Cairn side runs a loopback-only listener (bound to `127.0.0.1`, never `0.0.0.0`). A shared token (generated by Cairn at pairing, pasted into the EA's input once) authenticates the EA so another local process can't inject fake fills. Length-prefixed JSON frames; the listener rejects oversized frames.
- **Shipping the EA (built 2026-07-10):** `CairnBridge.mq5` and its one-page install guide ship **inside the installer** — `apps/desktop/resources/mt5-bridge/` is copied beside the app as an `extraResource` (`electron-builder.yml`), mirroring the vendored cTrader protos. This closes a P0 where installed builds shipped without the EA the Settings panel told users to copy. Settings → Integrations → MT5 shows the pairing token, the loopback address, a live "EA connected / last event Xs ago" indicator, and a one-click **Install Cairn EA** button that copies the EA (plus its compiled `.ex5` when a build ships one) into every auto-detected `MQL5/Experts` folder, with a per-folder **Open** button. Both the install and reveal actions are main-process only and confined to folders Cairn itself discovered (`findMt5ExpertsPaths`) — never a renderer-supplied path — so they add no arbitrary write/open sink. Implementation: `services/broker/mt5/installer.ts`; IPC `broker:installMt5Ea` / `broker:revealMt5Experts`; test `tests/unit/broker/mt5-installer.test.ts`.
- **Why not the MT5 Python package:** it's Windows-only, poll-based (seconds of lag, so no real-time prevention), and adds a Python runtime dependency. The EA bridge is instant, cross-platform where MT5 runs, and fits the no-extra-runtime posture. (If a future contributor wants the Python path as a fallback, it slots behind the same `BrokerAdapter` interface — but it is not the chosen path.)

### 2.2 cTrader — Open API (decided)

cTrader exposes the official, free **Open API** (OAuth 2.0 + Protobuf over TLS, with execution-event streaming). Cairn registers an application with Spotware, the user authorises their account once, and Cairn subscribes to execution events that arrive in real time.

- **Application credentials (built 2026-07-10):** the OAuth *application* client id/secret are resolved **keychain-first, with an env-var fallback** (`services/broker/ctrader/app-credentials.ts`). A stock install can paste its Spotware client id/secret in Settings → Integrations → cTrader — stored in the OS keychain via `keytar`, never in the SQLite settings table, never on disk — while `CTRADER_CLIENT_ID`/`CTRADER_CLIENT_SECRET` env vars remain a dev/CI fallback. This closes the P0 where an installed build (no env vars) could not connect cTrader at all. IPC `broker:setCtraderCredentials` / `broker:clearCtraderCredentials`; test `tests/unit/broker/ctrader-app-credentials.test.ts`.
- **Auth:** OAuth 2.0 authorization-code flow; the per-user access/refresh *tokens* are stored in the OS keychain via `keytar` (same mechanism Stage 18.4 uses for the data key), never in plaintext on disk.
- **Stream:** subscribe to order/position execution events; each maps to a `BrokerEvent`.
- **Caveat (network, not local):** unlike the MT5 bridge, the Open API is a cloud service — events transit Spotware's servers. This is unavoidable for cTrader and is disclosed in Settings. No Cairn vault content is ever sent to Spotware; the flow is read-only inbound.

## 3. The auto-log model (configurable)

**Decision:** support both behaviours, user-selectable in Settings → Integrations → "When a broker fill arrives". Default is **draft-awaiting-context**.

| Mode | What happens on a fill | Who it's for |
|---|---|---|
| **Draft awaiting context** (default) | The trade is created with all *mechanical* fields prefilled (pair, direction, lots, entry/SL/TP, exit, times, partials) and dropped into the **deferred-reflection queue** as `awaiting_reflection`. The trader still supplies the honesty fields — invalidation, emotional state, plan-followed, rules-broken, reflection — calmly, later. | Traders who want Cairn's discipline layer intact: data capture is automated, self-awareness is not faked. |
| **Fully auto-logged** | The trade is written complete. No follow-up required; it never enters the reflection queue. | Traders who want Cairn purely as a passive, zero-friction journal of record. |

This reuses the **two-phase logging** machinery already built in Wave 3 (`phase`, `awaiting_reflection`, `reflected_at` columns; `listAwaitingReflection`; the Review-screen queue and sidebar badge). A broker fill in draft mode is just Phase-1-by-machine: the gate's *mechanical* half is filled by the broker, and Phase 2 (the journal) is deferred exactly as a manual fast-path close already is.

**Honesty boundary (non-negotiable):** neither mode invents honesty data. Fully-auto leaves the honesty fields null/`unreviewed` rather than defaulting them to "clean" — a trade Cairn never asked the trader about must not silently claim the plan was followed. The composite score, A–F grade, and clean-rate analytics must treat `unreviewed` trades distinctly, never as clean. (`CLAUDE.md` §2.3.)

**What auto-log does NOT do:** it does not run the *pre-trade* gate. By the time a fill streams in, the order is already live at the broker — Cairn cannot block it. Auto-log serves job #2 (honest capture), not job #1 (prevention before the click). Job #1 for streamed trades is served instead by §5 (live detection). This distinction is stated plainly in the Settings copy so the trader is never misled into thinking auto-logging protects them in the moment.

## 4. The internal contract — one event shape, two sources

Both transports normalise to a single typed stream so the rest of Cairn is transport-agnostic. This extends the existing `BrokerAdapter` interface in `docs/integrations-future.md` §11.1 with the live half.

```ts
// packages/shared-types (reused by desktop; server untouched by this wave)
type BrokerEventType =
  | 'position_opened'
  | 'position_modified'   // SL/TP changed, or size added/reduced
  | 'partial_close'
  | 'position_closed'
  | 'heartbeat';

interface BrokerEvent {
  type: BrokerEventType;
  broker: 'mt5' | 'ctrader';
  brokerAccountId: string;
  brokerTradeId: string;      // broker position/order id — the dedupe key
  symbol: string;             // broker symbol, mapped to a Cairn pair downstream
  direction: 'long' | 'short';
  volumeLots: number;         // decimal-encoded downstream, never float in storage
  price: number;              // entry / modify / exit price for this event
  stopLoss: number | null;
  takeProfit: number | null;
  eventTimeMs: number;        // broker-reported time, UTC
  raw: unknown;               // original payload, retained for audit / reparse
}

interface LiveBrokerAdapter extends BrokerAdapter {
  supportsLiveStream: true;
  connect(config: BrokerConnConfig): Promise<Result<void>>;
  onEvent(handler: (e: BrokerEvent) => void): Disposable;
  status(): 'connected' | 'disconnected' | 'error';
  disconnect(): Promise<void>;
}
```

- Money/pips are **never** stored as float (`CLAUDE.md` §2.5 / §19.5). `BrokerEvent` carries broker-native numbers; the ingest service encodes to integer cents/pips via the existing `_shared/encoder.ts` from Wave 3 before any DB write.
- The ingest service runs in the **desktop main process** (it owns the socket / OAuth tokens and the SQLite write path). The renderer only receives a typed status + new-trade events over IPC.

## 5. Live detection — prevention, finally, in real time

This is the moat (`docs/roadmap-v1.2.md` §1; `CLAUDE.md` §14 #30). The existing rule engine already encodes the rules and already has real-time hooks for SL-widening and TP-narrowing on *Cairn-placed* drafts (Wave 2 item 4). Wave 4 feeds it the **live broker position** so the same rules fire on trades placed *outside* Cairn.

On each `position_modified` / `position_opened` event, the ingest service runs the matching evaluators and, if a rule is breached, raises a **non-blocking** real-time warning (Cairn cannot block a broker order — it can only alert):

- **SL widened against the position** — actual SL is further from entry than the planned/last-seen SL.
- **Size increased mid-trade** beyond tolerance.
- **TP cut toward entry.**
- **Over-trade** — this fill is past the account's daily-trade-limit.
- **Trading after the max-daily-loss circuit breaker** already tripped this session.
- **Trade outside the configured killzones.**

Warnings surface as a calm, mentor-voice toast/log entry (`CLAUDE.md` §1 voice: e.g. *"Stop moved against you on EURUSD. This breaks Rule 4 on this account."*) and are recorded as `rule_violations` against the trade so they show up in analytics and at reflection time. They are detections, not blocks — and the Settings copy says so.

To compare planned-vs-actual, a live broker trade needs a "plan". If the trader logged a Cairn pre-trade draft for the same symbol/direction shortly before the fill, the ingest service links the fill to that draft (so the real plan is used). If there's no matching draft, the *first* observed SL/TP/size becomes the baseline and subsequent modifications are measured against it.

## 6. Reconciliation, dedupe, and the Wave 3 boundary

Wave 3 already imports *closed* trades from statement files; Wave 4 streams *live* trades. They must never double-count the same trade.

- **Single dedupe key:** `brokerTradeId` (the broker position/order id), stored in the existing `external_ref` column on `trades` and `trade_partials` (added in Wave 3 migration 0008). A live-streamed trade and the same trade later appearing in a statement import resolve to one row via `external_ref` — `ON CONFLICT DO UPDATE`, never a second insert.
- **Symbol mapping** reuses Wave 3's `_shared/symbol-resolver.ts`. An unmapped symbol from a live fill creates the trade but flags it for symbol resolution (it does not silently drop the fill — same rule as import).
- **Source of truth on conflict:** if both a live stream and a statement describe the same trade with different numbers, the statement (broker's settled record) wins for monetary fields; the live stream wins for intra-trade timing/modification history. Documented and tested.

## 7. Sync interaction (v2.0)

Live-streamed trades are ordinary `trades`/`trade_partials` rows, so they flow through the Stage 18.6 sync engine exactly like any other trade — encryption-on-write enqueues them, and they converge across devices. The one requirement: the ingest service must write through the **same** `enqueueSyncOp` path the manual handlers use (see the import-adapter sync-gap follow-up), so a streamed fill on the desktop reaches the web app. No server change is needed — the server still only ever sees ciphertext.

## 8. Security & privacy posture

- **MT5 bridge is loopback-only.** Listener binds `127.0.0.1`, rejects non-local connections, authenticates the EA with a per-install pairing token, and frames input with a size cap. No inbound internet exposure.
- **cTrader tokens** live in the OS keychain (`keytar`), never plaintext. OAuth scopes are read-only.
- **No order execution, ever.** Neither adapter compiles an order-send path. This is asserted by a test that greps the bridge/adapter surface for broker write calls and fails if any appear.
- **No telemetry.** Connection status is local UI only; nothing about the user's trading is sent anywhere (`CLAUDE.md` §2.4, §14 #27).
- **Disclosure.** Settings states plainly, per platform, where data flows (MT5: stays on device; cTrader: transits Spotware inbound, read-only) and that auto-logging is capture, not prevention.

---

## 9. Why Wave 4 is isolated (and optional)

Waves 0–3 already removed ~80% of the friction with zero infrastructure. Wave 4 is the only wave that adds real moving parts (a shipped EA, an OAuth app registration, a long-lived listener) and the only one whose value depends on the user running a specific terminal. Per `CLAUDE.md` §14 #31/#33, the project must stay fully useful even if Wave 4 never ships. Nothing in Waves 0–3 may depend on it. Build it after v1.2 is "done" and tagged — before, after, or instead of the v2.0 cloud rebuild, the trader's call.

## 10. End-state criteria (Wave 4 "done")

Wave 4 is complete when:

1. A Cairn-bridge EA installs into an MT5 terminal and, on every fill, delivers a `BrokerEvent` to the desktop over loopback with token auth; Settings shows live connection status.
2. cTrader Open API connects via OAuth (read-only), tokens in the keychain, and streams execution events as `BrokerEvent`s.
3. Both sources normalise to the one `BrokerEvent` stream; the ingest service encodes money/pips to integers (decimal.js), never floats.
4. A fill in **draft-awaiting-context** mode creates a trade with mechanical fields prefilled, lands it in the reflection queue, and leaves honesty fields `unreviewed` (never defaulted to clean).
5. A fill in **fully-auto** mode writes a complete trade that never enters the queue; analytics treat its honesty fields as `unreviewed`, not clean.
6. The mode is a Settings toggle; copy states auto-log is capture, not pre-trade prevention.
7. Live detection raises non-blocking, mentor-voice warnings on SL-widen / size-up / TP-cut / over-trade / post-breaker / outside-killzone, recorded as `rule_violations`.
8. Live trades dedupe against statement imports via `external_ref`; no double-counting; round-tripped in tests.
9. No order-execution code path exists in either adapter; a test enforces this.
10. All five quality gates green (typecheck · lint 0 · unit/integration · build · smoke E2E), with the EA tested via a fixture event replay and the adapters tested against recorded payloads.
